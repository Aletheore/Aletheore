The adapter's in-process exception handling (Finding 1) covers every *catchable* failure - but a hard process kill (OOM-kill, SIGKILL, host crash) while a reservation is outstanding (the narrow window between `can_start_next_call()` returning `True` and the adapter's own completion/failure handling) leaks that reservation with zero trace, permanently, exactly like the original bug this class's own docstring says it was built to fix (the documented "$32 gap" across two real installations) - just via an uncatchable trigger instead of a catchable one. Confidence: confirmed the mechanism (DB-level deduction + Python-only release + no reconciliation sweep exists) by reading the real code; the actual trigger (hard process kill) was not reproduced live, so the probability/frequency of this in production is unverified - this is a structural gap, not an observed incident.

### db.py (full file, 2169 lines)

Reviewed in full: credit/spend reservation (`reserve_llm_spend`/`release_llm_spend_reservation`), all three advisory locks (`installation_spend_lock`/`repo_checkout_lock`/`wiki_write_lock`), review-comment idempotency, both model-output cache tables, wiki/docs upsert+prune functions, catch-up sweep queries, retention/cleanup jobs, and the remaining read/list helpers.

**Finding — real, verified gap, medium severity: `evidence_packet_cache` has no retention sweep, unlike every comparable table in this file.** `insert_evidence_packet_cache_row` (line 1742) writes one new row per cache-eligible AIRview writing-stage call with no corresponding delete anywhere - grepped this repo's `scan_worker/`, `app_server/`, and every migration file for any `evidence_packet_cache` DELETE/TRUNCATE/retention mechanism; none exists. Compare to its structural sibling `flash_review_cache` (built with the same embedder-identity column via migration 054, the same `list_recent_*_rows(limit=200)` lookup-cap pattern, the same `record_*_hit` function): it has `delete_expired_flash_review_cache` (line 2002), wired to a real scheduled job (`run_flash_review_cache_cleanup_job`, jobs.py:4417). That function's own docstring states the exact bug this finding is describing, just for the sibling table and already fixed there: *"previously unbounded, since the only thing limiting a lookup's read was list_recent_flash_review_cache_rows' LIMIT 200, which caps what one query returns, not what the table retains."* Every other growing table in this file has at least one bounding mechanism - `repo_history` and `endpoint_health` use a per-key row-count trim (`keep=N` + `OFFSET` delete), `sessions`/`webhook_deliveries`/`flash_review_cache` use a time-based sweep, `endpoint_health` uses both. `evidence_packet_cache` is the only operational/cache table with neither. Practical effect: unbounded growth over time for an active AIRview-using installation, and since the table's only index is `(installation_id, repo_full_name, created_at DESC)` with no `embedder` column included, the lookup query's `WHERE ... AND embedder = %s ORDER BY created_at DESC LIMIT 200` has to scan past an ever-larger run of non-matching rows to fill its 200-row cap after any future embedder switch (the exact scenario embedder-identity filtering was added for) - a real, compounding scalability cost tied directly to the missing retention sweep, not just unbounded disk growth. Fix shape: a `delete_expired_evidence_packet_cache(dsn, retention_days=30)` mirroring `delete_expired_flash_review_cache` exactly, wired to a new scheduled job the same way. Confidence: confirmed by reading every reference to this table in the codebase (all 4 functions, both migrations, the index definition) and the sibling table's own fix-commit docstring describing the identical bug - not inferred from a pattern match.

**Verified correct, no issues (worth recording so a future pass doesn't re-derive this):**
